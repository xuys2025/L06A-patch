# L06A `/data` 容量复核与功能预算

后续更新：用户批准日志治理后，已于 2026-09-30 03:01 部署 512 KiB 日志限额，可用空间升至 **2.97 MiB / 使用率 76%**。详见 [执行记录](LOG_GOVERNANCE_EXECUTION_20260930.md)。以下内容保留治理前的调查快照。

调查时间：2026-09-30 02:50–02:54，Asia/Hong_Kong。设备：L06A / AS06 VER0106，当前助手基线 `2026.09.30-final14-preserve-ducked-playback`。

本次只读检查设备与本地代码，保存调查文档；没有清理文件、修改配置、重启或更新设备。下列容量为现场快照，后续发布必须重采。

## 1. 结论

**空间确实紧张：`/data` 可用约 1.43 MiB、使用率 89%。现有语音流程、灯效、工具调用和音乐控制仍有继续改进的空间，但不适合在这个余量上直接叠加长期日志、录音、歌曲下载或本地大模型。**

功能数量不能直接折算成剩余容量。关键是新程序实际增长多少，以及是否增加持久数据。final13 与 final14 的助手二进制均为 10,027,168 bytes：一次有效的音乐修复并未增加文件大小；这说明修改现有逻辑通常比增加运行时、模型和缓存更容易容纳，但不能保证以后每版都不增长。

近期建议：先按已有存储计划治理日志，再分批做语音改进。现有低空间网络更新机制可以继续使用，不因本次容量快照立即要求重新线刷。轻量长期记忆则继续遵守已有容量门槛，不能把“逻辑可做”视为“当前可直接启用”。

### 日志已经有限额，但可以收紧

已核实设备正在使用的 `/usr/sbin/easy_logcut`，而不是名称相似但针对其他目录的轮转脚本：

- cron 每 5 分钟执行 `easy_logcut size`。
- 内存日志 `/var/log/messages` 超过 1,024 KiB 时压缩到 `/data/log`。
- 持久历史日志目标上限为 2,048 KiB；`LOGGEN=18`。它是轮转后清理的目标，不是每次写入前都生效的硬配额。
- 现有流程先压缩写入，再清空源日志，最后清理旧归档；没有在压缩失败后阻止清空源日志。

因此，**没有证据说历史日志会无限增长**。但它目前几乎占满自己约 2 MiB 的预算；一次性删旧日志后，正常轮转仍会重新积累。

建议按既有 S1 计划将必要日志归档到电脑，设备目标缩至 512 KiB，并补齐压缩失败保护、写入临时空间预算及重启后的持久生效路径。当前归档逻辑体积与 512 KiB 相差约 1.44 MiB，实际释放量必须实测；不把它承诺为确定新增 1.44 MiB 可用空间。S1 的可用空间目标仍沿用已有计划的至少 2.5 MiB。

## 4. 还能支持哪些工作

| 功能/工作 | 容量判断 | 约束 |
|---|---|---|
| 打断、会话归属、ASR 收尾、LED 修复 | 预计可继续，逐版核实 | 改现有逻辑；不要为诊断默认保存原始 PCM |
| 音乐聚合搜索、推荐/播放工具、当前歌曲感知 | 预计可继续 | 候选和短期状态放有限内存；音乐继续流式播放 |
| 音量、退出、短指令和更多模型工具 | 预计可继续 | 尽量复用 Go 与现有原厂接口；新增依赖前测 ARM 二进制增长 |
| 分句 TTS、连续对话、耗时统计 | 预计可继续 | 分句音频、队列与日志设上限；测并发运行时 RAM 峰值 |
| 轻量长期记忆 | 可设计/离线开发；当前不满足既定上线门槛 | 现有方案为活跃快照最多 256 KiB、约 200 条事实，写入峰值预算不超过 1 MiB；上线前目标空闲至少 4 MiB |
| 全天录音、全文聊天长期留存、离线歌曲库 | 当前存储不适合 | 必须另设外部存储与留存策略 |
| 本机部署大型 ASR、TTS、LLM 或向量模型 | 当前容量不支持这类扩展 | 保持现有云端推理路线，若要离线能力需独立硬件/模型评估 |

两个量级示例：16 kHz、16 bit、单声道 PCM 一分钟有约 **1.83 MiB** 原始数据；320 kbit/s 的四分钟歌曲约 **9.16 MiB**。这些是未计封装/压缩的内容量，用来说明为什么不能让音频长期写入 `/data`，不是对特定压缩文件是否能写入的实测结论。

现有三批语音改进在存储上没有发现必须整体搁置的障碍，但每批仍要按构建产物、临时数据和发布回退需求验收；不能凭当前余量保证尚未实现的程序一定装得下。

## 5. 网络更新的空间预算

当前 `low_space_update.sh` 的实际路径：

1. 新程序先上传 `/tmp/assistant-agent.new`。
2. 将旧程序备份到 `/tmp/assistant-agent.rollback`。
3. 停止相关服务，删除 `/data` 旧程序，再将新程序复制到原路径。
4. 检查哈希、程序配置和健康，失败时尝试从内存备份恢复。

这避免在 `/data` 同时保留两份 9.56 MiB 程序。本次版本的新旧二进制合计约 **19.13 MiB**，当前 `/tmp` 和可用内存足以容纳这部分；但每次更新还应检查服务/缓冲等峰值，而非仅看文件大小。

代码已有哈希与运行失败回滚，但尚未做系统化空间预检查。`/tmp` 回滚副本断电后丢失，因此不能将这个流程描述为持久 A/B 或断电原子更新。

建议把以下内容列入下次发布准备：

- 更新前记录 `/data`、`/tmp`、可用内存和新旧包大小，预算临时文件与回滚副本。
- 日志、短期历史和分句音频设总量上限；诊断导出至电脑，不长期堆在设备。
- 保留配置/日志写入余量。既有计划把低于 1 MiB 作为提前处置信号；这个值是项目运维约定，不是 UBIFS 的固定安全阈值。
- 当前约 1.43 MiB 余量不宜全用完。即使仅保留 1 MiB，新增持久内容的静态余量也只约 0.43 MiB，且仍须扣除后续轮转/更新临时需求。

## 6. 进一步扩容路线与排期衔接

遵循已有 [data 优化计划](../plans/DATA_PARTITION_OPTIMIZATION_PLAN.md) 和 [统一排期](../plans/L06A_NEXT_PHASE_SCHEDULE.md)，本报告补充 final14 新快照，不改变已约定的维护窗口和阶段状态：

1. **先做 S1 日志治理。** 投入较小，收益能直接实测；近期代码改进仍走网络更新。
2. **按需评估 S2：压缩保存、内存运行。** 本地 final14 gzip 测量为 4,020,938 bytes，约 3.83 MiB。但 UBIFS 本来就压缩，不能用 9.56 − 3.83 MiB 宣称实际收益。须设计启动、更新、持久回退及 RAM 峰值后再试。
3. **稳定版发布时评估 S3：把稳定程序放进 system1 基线。** 可以回收长期占用 `/data` 的覆盖程序，但必须重建并核对 system1 镜像容量、兼容性和恢复方案；不为本次调查单独安排线刷。若 S3 已解决空间，则不必重复实施 S2。
4. **长期记忆沿用既有 G3 门槛。** 容量验收前可以离线开发；不在当前 1.43 MiB 余量下启用持久记忆。详见 [长期记忆预算](../plans/L06A_LONG_TERM_MEMORY_PLAN.md)。

没有闲置 UBI 擦除块可直接扩 data；更改分区布局或减少坏块保留空间不列入本轮方案。
