# L06A 原厂唤醒、六麦阵列与灯控：只读逆向研究

研究日期：2026-09-30。对象：当前设备原厂 1.88.221 音频程序，以及备份中的 1.94.13 固件。研究方法为 ARM 反汇编、模型容器和文件系统解析、哈希比对、现有运行状态与日志核对。没有执行修改后的原厂程序，没有刷机、重启服务、改参数或开启录音。仅新增本报告及本地只读提取脚本。

证据等级：**确认**表示已由二进制、原始镜像或现场状态直接验证；**推断**表示有机制支持但没有场景对照实验；**未知**表示当前资料不足。以下 ELF 地址均是指定哈希样本中的虚拟地址，不是运行时 ASLR 地址，也不是通用补丁偏移。

## 结论与优先级

原厂唤醒的核心运算在运行 Linux 的主板侧 `mipns-xiaomi + libxaudio_engine.so`。上板的六麦负责拾音，按键和灯环各有独立控制路径；不能因为它们都在上板，就把唤醒算法也归到上板。

目前最值得研究的是**阵列输出给唤醒模型的音频质量，以及第二级复核的误拒绝**。还不能用现有日志证明具体哪一项造成用户现场漏醒，更不能承诺改善百分比。

已经排除几条容易浪费时间的路线：

- 两份原厂固件的音频库逐字节相同，切换到备份中的 1.94.13 不会带来新的库内唤醒模型或前端算法。
- 当前唤醒模型从库内加载，配置文件里的模型路径不是现成的换模型接口。
- `mipns-xiaomi` 帮助中的 `-t` 没有对应的有效处理分支，不能当作已接通的灵敏度旋钮。
- 原厂 DNN 唤醒增强实际走旁路，且两份镜像都缺少完整初始化器需要的一份权重。不能简单改一个调用就宣称恢复成功。
- 音频库里的 LED 设置 API 是日志桩；真正的灯控通过脚本、UBus、ledserver 和内核驱动。

## 原厂实际音频路径

```text
上板六麦
  → 主板 PDM/ALSA 采集与整理
  → 六路麦克风 + 播放参考
  → 按参考信号条件启用 Speex AEC
  → 声源定位/跟踪 + MVDR 阵列处理
       ├─ 较早的输出 → AGC → DNN-WE 旁路 → 本地两级唤醒
       └─ WebRTC 后置降噪 → AGC → DNN-VAD → 后续语音识别音频
                                                 └─ VAD 信息反馈给阵列处理
```

这是概念图；两条分支还经过缓存、重分帧和时序管理。第二条分支的 VAD 可能反馈影响阵列，因此不能声称后置降噪的任何变化都与唤醒完全无关。

**确认：唤醒没有直接使用 WebRTC 后置降噪之后的那一路。** `AFEEnhancementProcess` 在 `0x39664` 进行第一次 ISTFT，`0x39678` 调用 `webrtc_postfilter`，`0x39694` 进行第二次 ISTFT。两个输出分别重分帧、AGC，`0x397e4` 对第二路执行 DNN-VAD。后续每块 640 字节包含两段各 160 个 S16 样本，属于两路连续存放，不能按左右声道交错解释。唤醒线程 `0x1e99c–0x1e9c0` 取前半块。

`webrtc_postfilter` 并非空函数：其跳转最终进入 `WebRtcNs_ProcessCore`。初始化路径将 NS 策略设为 0。提高该策略首先改变的是第二路，不是一个已证明可提升唤醒率的开关。

**确认：原厂已有真正的阵列增强。** `manyears` 的调用链包含 `preprocessorProcessFrame`、`beamformerFindMaxima`、`SrpProcessCore`、`DnnVadFixMvdrProcess`、`Beamforming_MvdrBuff`、`MvdrReadBuffer`、`RnnHatRls` 和 `MvdrProcess`。不能把 DNN-WE 旁路解释成“原厂完全没有降噪或没有用六麦”。其中 `RnnHatRls` 的名字也不足以证明它是循环神经网络。

这些名称与 [ManyEars 项目的声源定位、跟踪、分离处理](https://github.com/introlab/manyears) 有对应关系，但本库含设备定制逻辑，不能视为未经修改的上游版本。

## 两级唤醒到底在做什么

`PaddyEngineImpl::ProcessTask`（`0x547e8`）管理两套 Rice 引擎：第一级持续处理；产生候选后，第二级从缓存特征回放复核，并可继续处理后续输入。两级均命中才产生正式确认路径。

| 项目 | 第一级 | 第二级 |
|---|---|---|
| 库内模型地址 | `0xc47e8` | `0x160a58` |
| 容器尺寸 | 639,597 字节 | 1,678,701 字节 |
| 版本 | `kws_s12a_1.1.7_0_level1` | `kws_s12a_1.1.7_0_level2` |
| 特征 | 16 kHz、40 维 MFCC | 相同配置 |
| 关键词序列标签 | `3,4` | `3,4` |
| FST 图 | 10 个状态、19 条弧、490 字节 | 同样的拓扑 |
| 关键词前进弧权重 | 2.25 | 4.0 |
| 相应自环权重 | 1.0 | 1.0 |

模型容器还包含转换模型、声学网络、先验和上下文。其转换模型使用 Kaldi 风格序列化标记，图使用 OpenFst `vector/standard` 格式。不能据此认定能把任意 Kaldi 模型直接替换进去。

**新增的确定优化入口：图权重。** 第二级从状态 0→2、2→3，直到 8→9 的八条关键词前进弧均为 4.0，第一级对应为 2.25。`ProcessEmittingViterbi` 的 `0x57a38–0x57a74` 将弧权重加入路径代价，并保留较小代价的候选。这与 [OpenFst 官方对 standard 弧及路径权重的说明](https://github.com/google-research/openfst/blob/main/docs/quick_tour.md) 一致。

这证明第二级的图侧偏置更保守，提供了可做离线实验的具体位置。**它不证明数值 4.0 有错误，也不证明把它改成 2.25 就会更好**：两级声学网络不同，分数分布不能直接等同；图改动可能增加电视对白误触发。

**确认：有复核等待窗口。** `RiceLoadModelBin` 在 `0x599a8–0x599b8` 将 `--wakeup-wait-frame` 默认设为 60，两个嵌入模型的 online_conf 未覆盖此值。`ProcessTask` 在 `0x551c8–0x55200` 比较当前帧与候选帧的间隔，超时分支 `0x550b0–0x550c0` 写入状态 2。该参数控制等待，不等同于声学灵敏度。当前不把 60 帧直接宣称为完整端到端响应延迟。

`IsKeyword`（`0x57d90`）基于 Viterbi 最佳 token 的词状态作判断，并回填分数及边界。没有发现一个可以直接解释为“用户说话达到某个百分比便唤醒”的简单阈值。

### 几个参数入口容易被误读

- `mipns-xiaomi` 的 getopt 字符串包含 `t:`，但实际选项分支未处理 `t`。帮助中出现 `-t <wakeup_threshold>` 不构成参数生效证据。
- `RiceLoadModelBin` 确实注册了 `--score-threshold`，默认 1.0，存于对象 `+0x3e8`；尚未证明所用解码路径读取并应用它。不能仅凭字符串存在就推荐调它。
- `xaudio_engine.conf` 写有 `model_path=/usr/share/xiaomi/wakeup_model.bin`，但当前初始化和模型加载分支选择库内两个模型；`PaddyEngineImpl::LoadModel`（`0x5477c`）仅返回 0。

## DNN 唤醒增强：旁路且缺权重

`AFE_DnnInit`（`0x51c1c`）调用 `DnnWeAllParaInit_pass`；`AFE_DnnProcessPostAgc`（`0x51d90`）调用 pass 处理路径。`0x53500` 的 pass 函数进行分块缓存和复制，没有执行完整神经网络推理。

完整初始化器 `DnnWeAllParaInit`（`0x52090`）构造八个权重路径。两份原始镜像均缺少：

```text
model_dense_2_0_transpose_iter2400000.txt
```

在 `0x52328` 的 `fopen` 之后，空指针走错误分支；`0x52344` 附近要求读取 `0x40000` 个 4 字节元素，即 1,048,576 字节。文件名虽然是 `.txt`，这里读取的是二进制权重，不能用文本、零填充或别的模型层顶替。

**修正先前可能过于乐观的方向：恢复原厂 DNN-WE 不能列为现成低成本修复。** 需要匹配的完整权重、正确初始化、两路音频时序和资源验证。原厂为什么旁路它——精度权衡、资源原因还是未完成产品功能——二进制不能直接回答。两份固件一致，只能说明这不是当前助手临时改坏的结果。

## 为什么电视、多人说话和风扇要分开处理

| 场景 | 已知机制 | 值得验证的方向 |
|---|---|---|
| 旁边电视、多人说话 | 声源选择与追踪并不等于识别“谁在叫我”；干扰本身也是语音 | 记录候选时的声源方向和稳定性，检查是否选中干扰源；再判断是否需要更适合竞争语音的前端或模型 |
| 风扇噪声 | 唤醒输入没有直接经过第二路的 WebRTC 后置降噪 | 对相同素材比较原唤醒流与温和降噪流；单独检查 AGC 抬噪、风直接吹麦和结构振动 |
| 音箱自身播放音乐或 TTS | 原厂有本机播放参考驱动的 AEC | 检查参考非零、同步、削波和实际消除效果 |

`xaudio_aec_thread` 在 `0x144dc–0x14518` 计算参考块样本绝对值的最大值，`0x14584` 与 10 比较，低于门限走复制/旁路并记录 `with aec=0`，进入 AEC 则记录为 1。随后按六路分别调用 AEC。这里的 10 是原始样本幅值门限，不是 dB。

Speex AEC 初始化参数是 frame 128、filter 4096、16 kHz；标准样本时基下对应 8 ms 和 256 ms。AEC 需要知道扬声器播放的参考信号，无法单凭本机参考抵消独立电视的全部对白。[Speex 官方文档](https://speex.org/docs/manual/speex-manual/node7.html) 明确描述了参考输入与时序要求。因此现场日志 AEC=0 本身不等于功能坏了，也不能靠强行开启 AEC 解决外部电视干扰。

## 上板硬件可以改什么

`ParametersLoadDefault`（`0x3bc40`）明确输出 Lx06 阵列位置标识，六个坐标为：

```text
(-0.0303,  0.0175, 0)
( 0,       0.0350, 0)
( 0.0303,  0.0175, 0)
( 0.0303, -0.0175, 0)
( 0,      -0.0350, 0)
(-0.0303, -0.0175, 0)
```

这些硬编码坐标呈六边形；按通常米制解释，对应约 70 mm 直径。它是软件假定的阵列几何，不是本轮卡尺测量结果。改变麦克风数量、布局、声道顺序或声孔结构，都需要重新核对阵列参数和声学响应。

现有代码含坏麦检测、重新设置阵列位置/增益和单麦回退分支。当前日志未报坏麦，不能因此断言六路增益、相位和拾音质量完全一致。上板合理的第一步是对通道一致性、声孔、密封与振动进行测量，而不是直接换更大阵列。暂无证据证明 LED 电源或 I2C 噪声造成了此次漏醒。

按键由 `/etc/init.d/touchpad` 启动 `/bin/touchpad`。该程序含 `/dev/input/event0`、`event1` 以及 UBus、mute 事件相关路径。它属于独立输入控制链；本轮未逐一恢复长按/短按状态机，也未证明麦克风静音键是否存在独立硬件断路，不能把软件 mute 路径当成硬件隐私开关证据。

## 现场只读核对

核对时间约 2026-09-30 12:27，当前版本 1.88.221：

- 原厂进程参数为 `mipns-xiaomi -c /usr/share/xiaomi/xaudio_engine.conf -l`。相对原厂启动脚本去除了 Opus 输出参数；核心库未换。
- 进程占用约 19,040 kB RSS，40 个线程。364,120 kB 是虚拟地址空间，不能说它消耗了这么多物理内存。
- ALSA PDM 采集处于 RUNNING，S16_LE、48 kHz、8 通道，period 512、buffer 8192。硬件有 8 个采集通道不能据此说它装有 8 个麦克风。
- 最近保留的周期日志：`total algo rtf` 约 0.44–0.47、`with aec:0`、`last_mic_detect_result:0`。RTF 不是整机 CPU 占用百分比，也不足以承诺新增模型有算力余量。
- 11:39:39.802 出现一级候选，frame=3232146，start=3232034，end=3232142，score=0.015216；约 615 ms 后出现 PNS `wakeup-1` 事件和 `suspect wakeup=2`。保留的筛选日志中未见对应二级成功或正式唤醒。

最后一条说明“候选后未确认”的路径确实出现过，但不知道当时是否有人呼叫，不能把它统计成真实漏醒。其约 615 ms 间隔与复核窗口机制相容，不足以独立证明全部时间都耗在窗口等待。

**命名陷阱：PNS 的 wakeup-1 / wakeup-2 不等于模型第一级 / 第二级。** mipns 的 main 将 `mipns_wakeup_1_cb` 注册给原厂音频引擎，把 `mipns_wakeup_2_cb` 注册给分布式唤醒组件。前者还会接收到疑似事件；正常确认之后才有多设备仲裁等后续流程。诊断时要分别跟踪 Rice 一级、Rice 二级、原厂确认、多设备仲裁和助手会话，不能只数 PNS 名字中的数字。

## LED 的实际控制路径

```text
原厂唤醒/会话事件
  → /bin/wakeup.sh（bf、think、ready 等）
  → /bin/show_led 或 shut_led
  → ubus call led show/shut
  → /bin/ledserver
  → /sys/devices/i2c-0/.../led_rgb
  → 原厂 AW20054 驱动 → 上板灯环
```

`wakeup.sh` 的 bf 分支传入角度；`show_led` 将其包装成 `L`、`pos` 等 UBus 字段。`ledserver` 在 `0x143c0–0x14440` 探测并打开候选 led_rgb 节点。

音频库中的 `set_led_lights`（`0x219fc`）、`set_led_angle`（`0x21a2c`）、`set_led_mode`（`0x21a5c`）仅打印日志并返回成功值，修改这些接口调用不会直接改善灯环。

其他工作已有原厂驱动反汇编和实测：18 个 RGB 像素，led_rgb 每次更新一像素，原厂接口整帧写入平均约 8.42 ms，足以支撑 25 ms 帧预算的方案。这个数据来自已有研究，不是本轮重新操作设备测得。详见 [播放和灯效研究](PLAYBACK_LED_ROOT_CAUSE.md)。其 5 秒空闲窗口未发现原厂抢写，不能推广到全部唤醒、告警和配网事件。

当前灯效优先级是单一控制者、状态切换连续性、按时间插值和真实事件对齐。没有必要因本次唤醒问题先更换上板或灯控芯片。

## 后续实验的具体入口与停止条件

此表是研究结论，不表示已经修改或部署。

| 优先级 | 实验 | 判定依据 |
|---|---|---|
| P0 | 将一级候选、二级确认、方向、麦克风状态、仲裁与助手会话用单调时间关联 | 先确定漏在模型前、复核、仲裁还是会话交接 |
| P1 | 用同一批带标签样本对比原唤醒输入与温和降噪输入 | 同时测漏醒率、误唤醒/小时、延迟和 RTF；不能只听声音是否更干净 |
| P1 | 仅对“一级正确命中、二级拒绝”的样本，离线扫描第二级图权重和复核窗口 | 有明确图入口；降低漏醒必须同时满足误唤醒限制，不能放行全部一级候选 |
| P1 | 电视/多人场景比较候选方向与实际呼叫方向 | 判断阵列选向错误与模型抗竞争语音能力，避免只调稳态噪声算法 |
| P2 | 检查六通道幅频、增益、异常/削波、声孔和机械振动 | 只有测出问题后再安排上板硬件改动或阵列重标定 |
| P2 | 有完整资源后再评估替换模型或恢复 DNN-WE | 需适配输入特征、解码图、模型格式和实时性；当前不能直接启用残缺权重 |

测试应区分安静、风扇、电视对白、多人竞争语音，以及设备自己播放音频；固定距离、角度、音量和说话人，保存每次真实呼叫标签，并保留无呼叫的背景段。尚未采集这些样本，所以本轮不给出成功率提升数字。
