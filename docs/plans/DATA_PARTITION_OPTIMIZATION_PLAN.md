## 4. S1：先控制持久日志

### 治理前已确认的机制

`/etc/crontabs/root` 每 5 分钟调用 `/usr/sbin/easy_logcut size`。当前内存日志超过 1 MiB 时轮转到 `/data/log`；历史日志目标上限为 2 MiB，代数参数为 18。

现有脚本先把新压缩日志写入 `/data`，再清空内存日志，最后清理超限归档。压缩失败没有阻止后续清空，因此空间不足时有丢失诊断记录的风险。已有总量限制，不能据此判断日志必然无限增长。

### 实施范围

- [x] 先将必要日志归档到电脑，再将设备端历史日志目标上限调整为 **512 KiB**，优先保留最新记录。
- [x] 将总量限制和按旧到新淘汰规则同时落地，避免只清理一次后恢复到 2 MiB。
- [x] 压缩和持久写入成功后才移除已改名的源日志；失败保留 RAM pending，下次定时调用重试。
- [x] 新归档先在 RAM 压缩/校验，写入前清理旧归档并预留空间；不依赖写满后再删除。
- [x] 持久入口采用 `/data/init.sh` 调用 helper 绑定覆盖只读 `easy_logcut`；卸载/重建与重复调用通过，整机冷启动待自然重启观察。

### 收益与验收

- 预计可释放约 **1.3–1.4 MiB 量级**，以实测为准；第一阶段目标是 `/data` 可用量达到 **至少 2.5 MiB**。
- 超限后能按规则淘汰旧日志；正常压缩和模拟写入失败的两条路径均通过验证。失败测试先在离线环境完成，不通过填满真实 `/data` 制造故障。
- 正常使用观察 24 小时，覆盖实际日志轮转；归档总量受控，容量没有异常持续下降。若未发生轮转，不能仅凭等待时间认定通过。
- SSH、管理页及语音/播放功能与实施前基线一致。
- 回滚时恢复原轮转逻辑和持久入口。已归档到电脑的旧日志不必全部重新写回设备。

## 5. S2：压缩保存助手程序

### 候选设计

将经过哈希校验的程序压缩包保存在 `/data`，启动时解压到 `/tmp` 后运行。当前 TTS 已使用压缩持久化、解压到内存的方式，但助手主程序仍需单独设计启动和故障恢复。

- [ ] 以维护时的最新程序重新测量压缩体积，测算 UBIFS 实际节省量，不直接用“9.56 − 3.81 MiB”作为收益。
- [ ] 预算正常运行和更新峰值：解压程序、待安装包、回滚副本、TTS、语音与播放缓冲都要计入；不能只看空闲状态的 `MemAvailable`。
- [ ] 校验压缩包及解压结果，防止启动损坏或未写完整的程序。
- [ ] 设计完整持久回退路径；不能把 `/tmp` 备份作为断电恢复的唯一来源。
- [ ] 验证固件内 factory 程序与当前语音配置是否兼容，不能仅因入口有 fallback 就认定可用。
- [ ] 更新工具支持空间预检查，并在写入前拒绝不满足预算的更新。预算至少覆盖新包、持久回滚需求、临时文件及安全余量。
- [ ] 在离线或可恢复环境验证各阶段中断；实机仅在维护窗口做正常更新、失败回滚与受控重启验收。

### 验收与取舍

目标是长期可用空间争取达到 **4 MiB 以上**，同时保留可靠更新与恢复能力。该数值是规划目标，不是任何版本都能更新的保证；部署门槛必须按当次包大小计算。

若收益不明显、内存峰值不足或无法实现可靠回退，则不切换此方案，保留 S1 成果并转入 S3 离线评估。回滚应恢复原启动入口和已知可用程序，不能只改一个路径。

## 6. S3：稳定固件收口

- [ ] 将稳定版助手作为 system1 内的基线程序，避免稳定程序长期重复占用 `/data`。
- [ ] 评估原厂 TTS 组件是否一并放回固件；配置、密钥和少量状态继续留在 `/data`。
- [ ] 现有镜像相对 system1 分区约剩 1.47 MiB，必须实际重建并校验大小，不能直接追加组件或预先承诺装得下。
- [ ] 保留网络更新覆盖能力，并明确何时回收已被新基线替代的覆盖程序。
- [ ] 先完成离线构建、镜像校验、依赖检查和恢复说明，再安排固件维护。

本项不涉及调整 MTD 分区布局，也不占用或改写 `boot0/system0` 原厂恢复槽。若需要改变此边界，应另立任务评估，不作为容量清理的附带操作。

## 7. 延期期间的风险与重新排期条件

治理前 88% 的快照不代表立即故障，日志当时已有轮转上限，没有证据推算具体写满日期。治理后为 76% / 可用 2.97 MiB；以下条件仍适用于后续容量管理。

但普通更新复制第二份程序时已发生空间不足，现有低空间更新通过把旧程序放到 `/tmp` 缓解，不能提供断电后的持久回滚保证。写满还可能导致配置保存失败、状态无法持久化和日志丢失。

以下是建议的重新评估条件，**不是自动执行规则，也不自动授权清理或更新**：

| 观察到的情况 | 建议行动 |
|---|---|
| 可用量低于 1 MiB，或出现持续下降 | 提前安排 S0/S1，先确认增长来源 |
| 出现 `No space left on device`、配置保存失败或日志写入失败 | 暂停新增部署和新增持久数据，优先安排空间处置 |
| 下次更新无法满足包大小与回滚空间预算 | 在更新前处理容量，不依赖试写来确认是否放得下 |
| 日志优化后仍无法留出更新余量 | 推进 S2，或在稳定固件发布时推进 S3 |

不直接清理仍在使用的语音记录、Mesh 程序、TTS 组件、配置、密钥和 SSH 访问材料；不削减 UBI 坏块保留空间来换取短期容量。
