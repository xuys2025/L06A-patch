## 1. 结论与决定

1. `/data` 紧张主要源于稳定程序和原厂语音组件长期作为覆盖文件放在小容量持久分区。单次清理只能缓解；下一版固件应吸收稳定修复。
2. 不修改分区布局，不削减 UBI 坏块保留空间，不占用 `boot0/system0` 原厂恢复槽。
3. 优先评估裁剪本机不使用的硬件驱动、工具和额外提示音包；第二批评估音箱自身的 Mesh/网关服务。保留米家控制、账号与共享通信依赖。
4. 把稳定助手、TTS 运行组件和启动修复整合进 `system1`；用户配置、凭据、绑定关系及少量状态继续保存在 `/data`。
5. 当前验证过的完整 `system1` 写入方法是 USB 线刷；助手程序已经支持网络更新。完整固件网络更新可开发，但现有原厂 OTA 不能直接套用。
6. 工程重构先解决“能否从源码重建当前可用设备”，再拆分内部模块；继续使用一个 Go 主程序，暂不引入设备端微服务。

|---|---:|---|
| `/data/assistant/bin/assistant-agent` | 10,027,168 bytes，约 9.56 MiB | 下一版固件替换 factory 基线，之后回收已被替代的覆盖文件 |

UBIFS 透明压缩会使逻辑文件大小、`du` 和物理空间占用不一致。不能把各行直接相加，也不能用文件大小保证删除收益；实施时以前后 `df` 为准。[Linux UBIFS 文档](https://www.kernel.org/doc/html/v6.15/filesystems/ubifs.html)

### 2.2 不优化的实际后果

- **更新余量已经不足。** 发布记录已有复制第二份约 9.5 MiB 程序时发生空间不足的案例。当前低空间更新把旧版本备份在 `/tmp`，删除目标后再写入；运行期间失败可以尝试恢复，但突然断电会丢失内存备份。
- **写满时配置和状态保存可能失败。** 即使单文件使用临时文件加改名，也必须先有空间写入临时文件；配置与密钥两个文件的整体事务还需单独设计。
- **诊断可能丢失。** 当前日志脚本先压缩到 data，随后清空源日志，缺少压缩失败保护。
- **可写区趋满会降低维护余量。** 更新包、临时持久文件和文件系统回收都需要余量；尚无数据证明当前发生明显性能下降。
- **不会因为 88%/89% 就必然立即宕机。** 日志已有上限，也没有足够长期趋势推算具体写满日期。

### 2.3 优化优先级

现有日志机制每 5 分钟检查一次，内存日志阈值 1 MiB、data 历史日志目标上限 2 MiB、代数参数 18。建议留存必要诊断后，将历史日志目标缩到 512 KiB，并补齐失败保护。收益约为 1.3–1.4 MiB 量级，仍需实测。

助手已经去掉调试段。对调查时版本进行纯内存 gzip 测量得到约 3.81 MiB，说明“data 压缩保存、tmp 解压运行”可作为过渡路线，但不能把 9.56 − 3.81 MiB 当作 UBIFS 确定收益，也不能省略启动回退和更新峰值预算。若固件发布临近，优先固化稳定版本。

详细 S0–S3 工作量、回滚要求与延期触发条件以[已有排期文档](DATA_PARTITION_OPTIMIZATION_PLAN.md)为准；本报告未创建自动执行任务。

## 3. 哪些内容迁入 system1

| 内容 | 新固件中的位置 / 策略 | 迁移要求 |
|---|---|---|

| `mico_aivs_lab`、`libaivs_sdk.so` | 恢复到系统原生程序与库目录 | 仅保留需要的语音能力，继续保护助手拥有的 speech socket |
| PCM 语音入口修复 | 固件内 PNS 配置和受控启动流程 | 保留原厂远场前端，明确单一麦克风/会话所有者 |
| 播放、音量、TTS 辅助脚本 | `/usr/libexec/assistant/` | 以经过验收版本为准，消除 data 与固件旧脚本漂移 |
| SSH 与服务启动修复 | init 脚本、正确持久路径 | 服务依赖就绪后启动，避免依赖固定 sleep 的偶然顺序 |
| 默认配置、管理页面 | 固件只读默认值 / 静态资源 | 默认配置只一处定义；新增版本迁移机制 |

**继续留在 `/data`：** 用户配置、API 凭据、管理令牌、SSH 身份材料、米家设备身份/账号绑定、网关配对关系，以及有明确上限的状态和诊断。录音缓冲、下载缓存、TTS 临时音频优先使用有上限的 `/tmp`；不得长期堆积。

当前构建脚本和镜像验证脚本都明确删除/断言不存在 `mico_aivs_lab` 与 `libaivs_sdk.so`。运行调试已证明原厂 TTS 需要恢复这些组件，所以两套脚本必须一起纠正。只把文件加回镜像而不修正启动所有权，会重新引入 ASR 通道争抢。

当前入口优先执行 `/data` 程序。新固件写入成功后，如果旧 data 覆盖仍在，设备可能继续运行旧程序。因此迁移需包含版本标识、配置兼容验证、成功启动判据，以及回收旧覆盖的步骤；保留“基线 + 可撤销热修复”的能力，但不能一直重复保存整个稳定版本。

### 4.4 功能级第二轮候选

音箱自身的 Mesh/网关可在维护窗口优先进行可回退停用验证。尤其要验证米家云控制、独立网关子设备、账号刷新和普通蓝牙音频；验证通过再从镜像及 data 移除相应组件。data 中 Mesh 文件约 1.60 MiB 是逻辑大小，不等于可回收物理容量。

MiPlay/多房间、DLNA、VoIP/通话等可在“明确不用 + 服务及动态依赖确认 + 回归验证”后单独评估。`idmruntime`、`mpap`、`mpas` 等不能本轮仅凭名字直接删除。语音通话组件组的独占压缩数据粗估约 0.57 MiB，优先级低于硬件和多余提示音包。

当前定制镜像中未发现已安装的 MPD、upmpdcli、shairport-sync、snapclient。工作目录存在旧构建材料不代表设备 rootfs 安装了它们，不将删除这些包计为当前收益。

上游 `xiaoai-patch` 的激进替换脚本会删除本项目仍依赖的原厂唤醒/音频组件，不能原样套用。

## 5. 线刷、网络更新与 OTA

### 5.1 当前边界

| 对象 | 当前能力 | 结论 |
|---|---|---|
| `/data` 助手和控制脚本 | SSH/SCP 网络部署、哈希检查、运行期间回退 | 已使用；低空间方案的备份位于 tmp，不能算断电安全双副本更新 |
| 完整 `system1` | USB 下载模式、写入、完整镜像长度回读校验 | 已验证的发布路径 |
| 完整固件网络 OTA | 原厂工具存在，但与定制分区保留策略不匹配 | 需开发、验证后才能作为正式发布路径 |

只读设备快照确认根挂载为 `mtdblock5`，`boot_part=boot1`。槽位为：

| 槽位 | kernel | rootfs | 用途 |
|---|---|---|---|
| boot0/system0 | mtd2 | mtd4 | 原厂 1.94.13，保留的恢复槽 |
| boot1/system1 | mtd3 | mtd5 | 原厂 1.88.221 内核 + 当前定制系统 |

旧 USB 调查报告记录的是刷入前的活动槽；不能把旧报告中的 system0 活动状态当作当前状态。

### 5.2 为什么不能直接用原厂 OTA

实际设备包含 `ota`、`flash.sh`、`boardupgrade.sh`、`mtd`、`nandwrite`、`fw_env` 等工具。读到的原厂升级逻辑是：验证并拆包，更新另一槽的 boot/rootfs，最后切换启动槽；包还可能携带 DTB/bootloader 更新项。它要求的包结构也不是单独一个任意 SquashFS 文件。

因此现在从 boot1 套用该流程会以 boot0/system0 为目标，与“保留原厂恢复槽”冲突。设备上没有安装上游仓库中的 `/bin/update.sh`，也没有完成通用 OpenWrt 平台升级适配；不能仅因为有 `sysupgrade` 文件就视为可安全使用。

原厂 crontab 仍含凌晨 3 点时段的 OTA 检查入口。真正升级还受脚本条件和云端响应限制，本次未判断它会实际刷写。下一版应明确关闭或替换自动原厂固件更新路径，同时保留米家控制所需通信；两者不能混为一项整体删除。

依据：[原厂升级脚本](../../local/analysis/L06A_1.88.221/original-system1-rootfs/bin/boardupgrade.sh)、[原厂 cron](../../local/analysis/L06A_1.88.221/original-system1-rootfs/etc/crontabs/root)、[网络助手更新](../../scripts/device/update_assistant_over_network.ps1)、[USB 固件写入](../../scripts/device/flash_system1_final.ps1)。

### 5.3 推荐后续路线

先用已经验证的 USB 方法发布一次重构固件，再开发专用 OTA：候选镜像有可信校验和型号/版本检查，在 RAM 维护环境中运行完整更新依赖，停止对待写 rootfs 的使用，将写入范围限定到 system1，并验证 NAND/ECC、回读、启动失败及断电恢复。上传包和维护环境的内存峰值必须单独预算。

保留 system0 只说明存在原厂恢复资源，不自动证明定制更新失败后能无人值守切回。启动计数、健康确认、回退触发与 USB 救援都要实测。把两个槽都改为定制 A/B 也可研究，但会放弃驻留原厂恢复槽，属于另一项架构决定。

**结论：这台硬件并非只能线刷，但我们当前还没有验证可用的完整系统网络 OTA。**

## 6. 项目为什么显得零散，以及重构方向

目前更接近“原厂底座 + 逐步修复的运行补丁”，并非没有架构。问题是工作目录、镜像构建和设备运行状态之间缺少统一版本关系。

| 问题 | 现有证据 | 建议 |
|---|---|---|
| 当前可用状态不能由旧镜像流程完整复现 | 构建删除 TTS 组件，设备又从 data 恢复；原始镜像报告仍是 final3 | 建立唯一发布入口，冻结 source / overlay / 配置版本 / 工具链 / 镜像哈希清单 |
| 工程材料混杂 | 根目录源码、固件备份、工具链、实验脚本和部署材料并存；仅嵌套上游仓库有自身 Git 历史 | 为自有源码和发布脚本建立明确版本管理边界；备份和私有配置分别管理，迁移时保留现有材料 |
| 会话控制集中且入口不一致 | `agent.go` 同时管理原生/备用语音、历史、ASR/LLM/TTS、灯效和音乐恢复；HTTP 文本直接路由 | 统一会话与音频仲裁，由一个状态机决定收音、播报、音乐和事件优先级 |
| 音乐解析与播放器耦合 | `music.go` 集中自然语言规则、三平台搜索、合并、解析、队列和播放控制 | 分离来源适配、候选排序、队列状态和播放器接口 |
| 工具机制尚不通用 | 只支持结束对话和音乐相关工具；路由只取第一项工具调用 | 新增受限工具注册/执行层，支持参数校验、执行结果回传与有界多步调用 |
| 配置与 UI 难维护 | Go 和 JSON 默认值并存；无显式 schema 版本；HTML 内嵌在 server.go | 单一默认定义、配置迁移、事务保存；管理页作为独立静态资源编入程序 |
| 健康与验收粒度不够 | `/health` 只返回 ok；历史音乐测试曾只凭 status=1 判定定位 | 区分存活、就绪和实际功能；协议测试、集成证据、现场验收分别记录 |

建议目标结构仍是一个设备端 Go 可执行文件，内部按 `session`、`audio`、`speech`、`llm`、`tools`、`music`、`home`、`config`、`httpui` 分工；这些是建议职责，不要求一开始建立全部包。先抽清接口和所有权，再逐步搬代码，避免整项目重写。

米家基础控制优先复用音箱已有的原厂文字指令链路，不以 NAS 或 Home Assistant 为前提。未来若增加大型知识库、长期记忆或更多外部服务，可选用轻量 NAS/家庭服务器后端。设备端专注拾音、灯效、播报、播放控制、鉴权和必要的降级能力。已有源码规模不足以证明需要设备端多进程微服务。

当前新增测试和调试正在推进；本文不把较早“测试不足”的观察当成最新测试覆盖率结论，也没有在其他 Agent 工作期间重跑测试。

## 7. 建议相对排期与交付门槛

具体维护日期待定；以下为单人有效工作量粗估，不含长时间观测、未知原厂兼容问题和现场等待。阶段可拆分，不能据此自动开工。

| 阶段 | 主要内容 | 工作量估计 | 完成判据 |
|---|---|---:|---|
| F0 | 冻结当前可用版本，记录米家/音频依赖和验收基线 | 0.5–1 天 | 版本清单、恢复材料、净化器等具体型号与独立网关清单 |
| F1 | 日志治理；稳定程序、TTS 和启动修复收口 | 1–2 天 | 可重复构建，容量和依赖检查通过，配置迁移可回退 |
| F2 | 按本机 profile 裁剪驱动和额外提示音 | 0.5–1 天 | 实际镜像大小合格，动态依赖完整，无米家组件误删 |
| F3 | 维护窗口线刷与完整回归 | 0.5–1 天，另观察 24–48 小时 | 唤醒、对话、点歌、打断恢复、蓝牙、AUX、按键、米家控制和网关回归 |
| F4 | 内部模块重构与功能扩展 | 按能力分批 | 每批沿用同一发布和验收流程 |
| F5 | 专用系统 OTA 原型 | 3–5 天初步验证，可靠性验证另计 | 限定分区、完整校验、失败恢复、断电场景均有证据 |

发布门槛：镜像能够完整解包并匹配清单；程序与配置兼容；不用 data 覆盖也能正常启动；原厂恢复槽保持完好；每项保留功能都有实际结果。米家控制是必验项，不以“相关进程还在”替代。
